# Toto 提醒机制调整方案

## 1. 目标与范围

本方案记录已确认但尚未完成的 Toto 提醒改造。实现后：

- 每个到期事项使用独立提醒窗口，只显示事项内容、计划时间、备注，以及“收到”“稍等”。
- 移除事项提醒的系统通知、主界面提醒横幅；每日开始盘点和结束复盘也只使用独立弹窗，不发送系统通知、不唤出主界面。
- 使用最近到期时间优先的队列及可重新安排的唤醒机制，替代事项提醒的 15 秒轮询。
- 未确认提醒可在应用重启后恢复；同一事项同时最多一个提醒窗口。
- 窗口不抢占其他应用焦点，不强制保持全局置顶；提醒窗口之间按出现顺序管理层级。

不改变其他工具的通知、后台演示任务，也不移除整个系统通知插件。每日盘点不增加“稍等”，保留现有内容和关闭行为。

## 2. 当前代码与未完成事项

以下以实施时重新检查的源码为准：

| 位置 | 当前行为与差距 |
| --- | --- |
| `src-tauri/src/lib.rs` 的 `toto-reminders` | 每 15 秒调用 `mark_due_reminders`，将多个事项内容拼接后发送事件；同时检查每日盘点。 |
| `src-tauri/src/toto.rs` | 到期时先将事项标记为“已提醒”并写回 CSV，再返回事件；尚无待确认状态、稍等或恢复协议。 |
| `src-tauri/src/reminder_queue.rs` | 已有基于 `BinaryHeap` 的队列和稍等计算的基础实现及两个单元测试，**尚未接入实际调度**。 |
| `src/App.tsx` | 主窗口监听事项提醒并创建窗口；每日盘点仍在主窗口内以 `TotoDailyReviewDialog` 展示并调用 `showMainWindow()`。 |
| `src/services/desktop.ts` | `openTotoReminderWindow` 复用单一 `toto-reminder` 窗口并合并内容。 |
| `src/components/tools/TotoReminderWindow.tsx` | 展示合并文本表格，尚无单事项详情、收到和稍等操作。 |
| 已完成的局部调整 | 事项提醒的系统通知与主界面横幅、每日盘点的系统通知已移除；这不代表完整方案已实现。 |

风险：现有代码先标记“已提醒”再发事件，若事件未被接收、窗口创建失败或应用退出，可能丢失提醒。CSV 事项操作多处采用加载、修改、整体写回；只在新增提醒代码中加锁不足以防止其他写入覆盖。

## 3. 已确认的产品规则

### 3.1 事项提醒

1. 每个事项最多一个活动提醒窗口。多个事项即使不是同一时刻到期，只要窗口仍打开，都参与位置和层级分配。
2. 弹窗展示完整的事项内容、计划时间和备注；允许换行和必要滚动；无计划时间或备注显示“无”。
3. “收到”、右上角关闭和 `Escape` 均视为确认，此次提醒不再重复；只有“稍等”重新安排提醒。
4. 未确认状态必须持久化；应用异常退出或正常退出后，下次启动重新展示。
5. “稍等”读取**点击时** Toto 设置中的当前默认提前提醒分钟数 `m`，间隔 `x = max(2, floor(m / 2))`。
6. 新提醒时间 = 点击时的真实本地时间截去秒和亚秒 + `x` 分钟。例如 `10:05:47`、`x=2` 得到 `10:07:00`；实际等待不一定满两分钟。
7. 可以在计划时间之后继续稍等，直到收到，或事项完成、取消。
8. 稍等必须先成功保存，再关闭窗口；失败时保留窗口并显示错误。事项在窗口打开期间被编辑、完成或取消时，旧窗口不得覆盖最新状态。

### 3.2 窗口位置和层级

- 第一个窗口在当前显示器工作区居中，之后依次向右下偏移；建议每级偏移量集中定义，例如 24 逻辑像素，最终由视觉验收确定。
- 第 2、3、4 个占用不同偏移位置；第 5 个及以后与第 4 个位置重叠。
- 已打开窗口不因其他窗口关闭而移动；新窗口优先使用空出的前四个位置。第 4 位置可能有多个窗口，不能在其中一个关闭时错误地释放其他窗口的占用。
- 新窗口不强制全局置顶、不抢其他应用焦点；用户主动回到 Toto 提醒时，在提醒窗口之间尽量保持先出现者位于后出现者之上。
- 层级和位置要在窗口创建、关闭、失败、恢复时统一维护；实际 Windows/WebView2 行为必须验证，不能仅凭 Web DOM 的 `z-index` 推断跨窗口层级。

### 3.3 每日盘点

- 独立桌面弹窗，保留现有开始盘点／结束复盘内容及关闭行为；无稍等。
- 不发送系统通知，不显示主界面提示，不通过唤出主界面承载弹窗。
- 保留工作日、定时和每天去重设置；事项提醒调度的改动不能让每日盘点漏触发或重复触发。

## 4. 后端状态与兼容性

### 4.1 状态模型

建议将事项提醒建模为以下语义，具体存储编码需要在实现前对现有 CSV 和外部兼容性验证：

| 状态 | 含义 |
| --- | --- |
| 无提醒 | 未设置提醒时间，不入队。 |
| 未提醒 | 等待 `reminder_at` 到期，进入优先队列。 |
| 待确认 | 已到期、尚未收到用户确认；重启后恢复窗口，不按普通到期队列重复创建。 |
| 已提醒 | 用户已确认，不再入队。 |

转换：`未提醒 → 待确认 → 已提醒`；稍等为 `待确认 → 未提醒` 并更新 `reminder_at`；完成／取消将事项移入历史并撤销其待提醒或待确认任务。编辑提醒时间时，以最新事项状态重新计算是否应入队或关闭旧窗口。

**兼容要求：**

- 读取现有 CSV、既有“未提醒／已提醒／无提醒”状态及历史归档；不得将旧的“已提醒”自动转换成“待确认”，以免历史提醒被重放。
- 优先评估沿用现有 CSV 字段保存新状态是否会影响导入、外部使用和版本兼容；若需新增字段或独立状态文件，须定义版本、迁移和回滚，不得直接丢弃未知列或旧数据。
- 以事项 ID 加上提醒版本或持久化代际作为操作令牌；窗口提交时后端重新读取并核验 ID、状态和版本。版本不匹配时返回明确结果，禁止旧窗口用旧快照整条覆盖事项。
- 将提醒记录和事项状态的持久化边界设计为可恢复的一致性协议；如跨文件无法原子提交，需定义操作顺序、崩溃恢复和幂等处理，而不是假定多文件写入是一个事务。

### 4.2 写入并发与失败

- 统一序列化**所有**涉及活动事项／历史事项／提醒状态的读改写，包括新增、编辑、完成、取消、到期转换、收到和稍等；审查已有所有调用入口及配置修改，不只锁住新增命令。
- 锁内重新读取最新数据，校验事项仍存在且状态／版本符合预期，再做最小修改并原子写入；避免根据前端传回的完整事项覆盖最新内容。
- 锁顺序固定，避免死锁；文件 I/O 失败不得先更新内存队列或关闭窗口。若跨文件操作在部分提交时失败，应保留足够的恢复信息并测试。
- 数据目录切换、外部文件修改和导入也须明确同步策略。实现前检查当前目录迁移和外部变更支持，不应假定只有单一写入来源。
- 稍等或确认与完成／取消竞争时，按串行化后的实际顺序判定；如果事项已移入历史，提醒操作返回“事项已结束”，不重新创建事项。

## 5. 优先队列与唤醒

1. 在 Rust 后端以 `reminder_queue.rs` 的 `BinaryHeap<Reverse<...>>` 为基础维护最早到期项；条目至少包含事项 ID、到期时间和版本。队列仅是内存索引，持久化数据才是事实来源。
2. 应用启动时读取持久化事项：重建“未提醒”队列，并独立恢复“待确认”窗口。读取或创建窗口失败应记录错误并保留待恢复状态。
3. 一个异步调度任务等待队首到期；队列为空时等待通知。新增、修改、稍等、完成／取消和数据目录变化后发送唤醒信号，重新计算队首等待时间。到期时一次处理所有已到期项。
4. 出队后在写锁内重新核对版本、状态和提醒时间；过期条目直接丢弃。先持久化“待确认”，再请求创建窗口；创建失败不转成“已提醒”，并保留重试／恢复路径。
5. 挂起恢复、系统时钟或时区变化时重新计算等待并补发已到期事项。需要确定 Windows 可用的恢复／时间变化通知及 Tauri 集成方式；如无法可靠监听，可增加**低频校正机制**作为兜底，但不得重新依赖固定 15 秒全量扫描作为主调度。
6. 现有提醒时间为本地无时区字符串（`NaiveDateTime`），系统时间变化和夏令时可能产生重复或不存在的本地时间。迁移为绝对时刻前须定义旧数据解释、时区来源及 DST 策略；不要把无时区字符串直接当成 UTC。至少为本地比较、休眠恢复及 DST 边界建立明确测试。
7. 定时器只能尽力在到期时唤醒；系统休眠、进程暂停或系统负载均可能延迟。恢复后必须补发，不承诺实时系统级精度。

## 6. 窗口与前端

### 6.1 单事项提醒

- 为每个事项生成安全、稳定且可映射回事项 ID 的窗口标识；Tauri 能力配置需显式覆盖这些动态窗口，避免权限匹配遗漏。不要把原文作为窗口标识或可信状态。
- 建立窗口管理器，统一处理活动窗口注册、并发创建去重、槽位分配、创建失败清理和关闭事件。操作通过事项 ID／版本向后端请求，窗口内容可以刷新，但不可将旧快照作为写入依据。
- 窗口创建需在正确的 Tauri 线程／运行时执行，并验证应用启动早于前端监听、主窗口隐藏或前端重载时也不会漏事件；不要依赖仅向主窗口发一次不持久的事件。
- “收到”、关闭按钮、Escape 走同一个幂等确认流程；同时避免系统关闭事件和按钮重复提交。持久化失败时不得假装确认成功。
- “稍等”调用后端原子操作；后端读取**当前设置和真实点击时间**，成功后通知调度器并允许关窗；显示错误时保留窗口及重试能力。
- 全文区域使用公共 Ju 组件和设计令牌，长文本换行、允许滚动，按钮在键盘下可操作。显示数据更新或事项结束时，窗口应及时刷新或关闭。

### 6.2 每日盘点窗口

- 将 `TotoDailyReviewDialog` 的内容提取为独立窗口可复用的视图，接收结构化盘点数据；窗口关闭不唤出主界面。
- 盘点触发记录和窗口创建之间需要考虑失败：当前 `check_daily_reviews` 在发送事件前写入当日已触发标记，创建失败时可能丢失盘点。实现应定义可靠投递或恢复策略，并保留现有去重语义。
- 从 `src/App.tsx` 移除主窗口盘点队列、`showMainWindow()` 及不再使用的监听；检查托盘启动、主窗口未显示和退出流程。

## 7. 开发步骤

1. **建立回归基线**：运行现有前端、Rust 和相关端到端测试；记录当前 CSV、历史归档和每日盘点兼容行为。
2. **持久化与并发**：实现待确认状态、版本检查、所有相关事项写操作的统一序列化和幂等命令；完成旧数据迁移及崩溃恢复测试。
3. **队列调度**：接入现有队列，加入重建、变更唤醒、过期条目校验和时钟／休眠恢复；将每日盘点从当前共用的 15 秒任务中妥善拆分，避免功能丢失。
4. **独立事项窗口**：实现窗口管理、位置分配、收到／稍等、关闭及错误处理；测试焦点和跨窗口层级。
5. **独立盘点窗口**：迁移既有内容和关闭行为，移除主界面盘点对话框与相关监听；验证定时及去重。
6. **端到端与人工验收**：运行自动化检查及实际 Windows/Tauri 测试；浏览器预览不能验证原生窗口、系统休眠和跨窗口焦点。
7. 按当前工作约定，默认执行编译和测试，**不自动打包 EXE**；只有明确要求时才打包。

## 8. 测试与验收清单

### Rust 单元／集成测试

- 队列排序、同一时刻多个事项、空队列、新队首唤醒、过期版本跳过。
- 事项到期后持久化待确认；窗口创建失败和重启后恢复；确认幂等；不重放旧“已提醒”数据。
- 稍等 `3→2`、`5→2`、`10→5` 分钟，秒截断、跨日／跨年、过计划时间及设置变更后的实时读取。
- 稍等／确认分别与编辑、完成、取消竞争，确认无丢失更新、不会复活已结束事项；文件写失败、部分写入及恢复。
- 时间前后调整、时区和 DST、睡眠恢复后的补发；旧 CSV、历史文件及数据目录切换兼容。
- 每日盘点工作日、当天去重、创建失败与恢复。

### 前端和 Windows/Tauri 验收

- 多事项独立显示、内容／备注换行与长文本滚动；收到、关闭、Escape 和稍等结果一致且错误可见。
- 同时到期和不同时间到期的 A–F：位置依据当前窗口分配，前四个位置和第五个重叠规则正确；关闭后新窗口使用空位。
- 在其他应用操作时产生新提醒：不抢焦点、不强制全局置顶；切回提醒后验证窗口之间的前后顺序。
- 新增／编辑／完成／取消／稍等后队列及时更新；窗口创建失败、应用重启和睡眠恢复不漏提醒、不重复开窗。
- 每日盘点仅出现独立弹窗，不发送操作系统通知、不唤出主界面。
- 执行 `pnpm build`、`pnpm lint`、相关前端测试、`pnpm rust:check`、`pnpm rust:test` 及适用的端到端测试；记录 Windows 人工验收结果与尚未验证的限制。
